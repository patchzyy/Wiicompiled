# Region support

WiiCompiled recompiles one Mario Kart Wii executable per region. The four retail regions are:

| Region | Game ID | Project                 | Region header                     |
|--------|---------|-------------------------|-----------------------------------|
| PAL    | RMCP01  | `projects/mkwii`        | `runtime/include/region/rmcp01.h` |
| NTSC-U | RMCE01  | `projects/mkwii-ntsc-u` | `runtime/include/region/rmce01.h` |
| NTSC-J | RMCJ01  | `projects/mkwii-ntsc-j` | `runtime/include/region/rmcj01.h` |
| NTSC-K | RMCK01  | `projects/mkwii-ntsc-k` | `runtime/include/region/rmck01.h` |

The same runtime source builds all four. Nothing in the runtime is `#ifdef`-ed per region, and
the build pipeline is the one `projects/mkwii` already uses: translate the project, then build
`runtime/`. Which region the runtime binds to follows from the project (see below), so building
another region is only a matter of translating its project instead of `projects/mkwii`.

## The problem

The runtime's HLE stubs have to name addresses inside the guest executable: the function they
replace, a global they read, the queue they walk. Those addresses differ in every region, because
each region's executable was linked separately.

The naive fix - writing the address as an offset from a register that is constant at run time,
usually `r13` (`_SDA_BASE_`) or `r2` (`_SDA2_BASE_`) - looks region-independent and is not. The
small-data blocks do not hold the same objects at the same offsets in every region. RMCK01 in
particular keeps a large part of `.sbss` 0x20 lower than PAL, NTSC-U and NTSC-J do.

That is not a theoretical concern. It is what kept Korea from booting:

* `__OSInitSTM`'s stub wrote the two `/dev/stm` handles at PAL's `r13-0x62c8` / `-0x62c4`. In
  RMCK01 that is `OSDisableScheduler`'s nesting count, so the scheduler was permanently disabled
  and the game hung in `OS::Init`.
* The ISFS stub wrote the filesystem fd and heap state at PAL's offsets, which in RMCK01 land on
  unrelated globals. The filesystem client never came up and the game showed the "cannot read or
  write the Wii system memory" dialog.
* The alarm stubs walked `OSAlarmQueue` at PAL's `r13-0x6360`. In RMCK01 that is a string table,
  so the queue walk faulted on `0x524D4353` ("RMCS") every frame.
* `OSSetPowerCallback`'s stub kept the callback pointer and the "handler registered" flag at
  PAL's `r13-0x62b8` / `-0x62c0`; RMCK01 keeps both 0x20 lower.

Each of those failed far away from its cause, and each looked like a different bug.

## The mechanism

Every guest address in the runtime is written as its **PAL address**, used purely as an identity -
a stable name for "that object", not a claim about where it lives:

```c
constexpr uint32_t kAlarmQueueAddr = MKW_GADDR(803868A0);   // the address, for this region
InvokeDirectCpu<MKW_GADDR(801949B8)>(ctx);
extern "C" void MKW_GUEST_FUNC(801A0620)(CpuContext* ctx); // the translated function's symbol
```

`MKW_GADDR(pal)` and `MKW_GUEST_FUNC(pal)` (`runtime/include/region/guest_region.h`) paste onto
`MKW_G_<pal>` / `MKW_F_<pal>`, which the generated per-region header defines:

```c
#define MKW_G_803868A0 0x803748C0u   // rmck01.h
#define MKW_G_803868A0 0x803868A0u   // rmcp01.h - PAL maps every identity to itself
```

PAL therefore compiles to exactly the constants it did before the mechanism existed. The region
headers also carry the handful of region *facts* the HLE reports to the game (`MKW_REGION_*`: game
code, TV format, the SC area / game region / product code, the initial MEM1 arena low address).

Which header applies is decided by the translation project, not by a build flag. The project's
`runtime.guest_address_table` names the header; the translator resolves the runtime's native
registrations through it (`Translator.Core/GuestAddressTable.cs`) and writes it into
`generated/RuntimeConfig.h` as `MKW_GUEST_REGION_HEADER`, which `guest_region.h` includes. The
runtime is therefore always built against the executable `generated/` was translated from.

The headers are generated by `tools/region/gen_region_headers.py`, which scans the runtime for
`MKW_GADDR` / `MKW_GUEST_FUNC` tokens and resolves each one. It currently finds **748 identities
(619 code, 129 data)**. An identity that cannot be resolved is an error, not a silent zero.

## Where the addresses come from

**Code addresses** come from the chunk tables in `tools/region/port_map.py` - contiguous ranges
mapping PAL text to each region's text, validated against that region's executables. The tables
are vendored from mkw-sp's `port.py` (MIT; see `THIRD-PARTY-NOTICES.md`). `port_map.py` ports the
PAL function map through them and keeps only entries the target binaries vouch for (call and
relocation targets, exception-table records, function-pointer tables, or at least a terminator
followed by a decodable first instruction); `projects/mkwii-ntsc-*/MAP_REPORT.md` has every
number and every dropped entry.

**Data addresses** are harder: chunk tables are function-granular, so they say nothing reliable
about `.data` / `.bss` / `.sdata`, and inside a function whose length changed they are not even
instruction-exact. So data addresses live in per-region tables:

* `projects/mkwii-ntsc-u/data_addresses.txt` is the **source of truth**, built by hand. For each
  PAL global it records the NTSC-U address *and the instructions that prove it*.
* `projects/mkwii-ntsc-j/data_addresses.txt` and `.../mkwii-ntsc-k/...` are **generated** from it
  by `tools/region/port_data_addresses.py`, which re-derives every address from that region's own
  shipped executable. Do not edit them by hand.

### Verdicts

The porter labels every row with how it was established, strongest first. It never guesses: a row
it cannot establish is written out as `UNRESOLVED`, which then fails header generation.

| Verdict | Meaning |
|---|---|
| `PROVEN` | The instruction at the ported reference site forms exactly this address, **and** the independent chunk-table port agrees. Two derivations, one answer. |
| `CALIBRATED` | The reference site reproduces the hand-verified NTSC-U address, so its decode is trusted here even where the chunk table has no mapping. |
| `MATCHED` | The reference site's instruction window, with region-varying fields masked out, occurs exactly once in this region's code; the displacement was read from it. Resolves globals inside functions whose length changed. |
| `ANCHORED` | A fixed offset from a resolved neighbour, where the same offset holds in the verified NTSC-U table. |
| `SECTION` | A section boundary, taken from the region's own section table. |
| `SECTION-RELATIVE` | Same offset within the same named section. Bounds-checked; weaker, and labelled as such. |
| `CHUNK-ONLY` | Chunk-table port with no reference site confirming it. Weakest. |

Current spread for RMCK01: 83 `PROVEN`, 10 `CALIBRATED`, 9 `ANCHORED`, 4 `SECTION`,
6 `SECTION-RELATIVE`, 17 `CHUNK-ONLY`, 0 unresolved; RMCJ01: 90 / 3 / 9 / 4 / 6 / 17 / 0.

### Masked instruction matching

The compiled instruction stream for the same SDK source is identical between regions apart from
the fields that legitimately move: SDA displacements, branch targets, and `lis` high halves. Mask
exactly those and a window around a reference site becomes a signature. If it occurs **exactly
once** in the target region's code, that occurrence is the same instruction, and the displacement
read from it is that region's address. Zero matches or several are reported, not guessed at.

Only sites that reproduce the known NTSC-U address are used as signatures. An uncalibrated site
forms some *other* object - several GX globals are reached through a pointer cell, so the site
loads the cell rather than the object - and matching one resolves the wrong address confidently.

## Things this has already caught

Besides the Korea bugs above, naming the EGG fog constants by identity found a latent **NTSC-U**
bug: those three `.sdata2` floats sit 8 bytes further from `r2` in NTSC-U than in PAL/NTSC-J/NTSC-K,
so the hardcoded PAL offset read `176.0 / 176.0 / 1.0` where every region should read
`0.0 / 0.99 / 0.5`.

## Regenerating

The tools are plain Python 3 (standard library only). They read the region's `main.dol` and
`StaticR.rel` from an extracted disc you own; nothing from the disc is written back into the
repository except addresses.

```sh
# Port the PAL function map to each region and validate it against that region's binaries.
python3 tools/region/port_map.py --region E --disc-root /path/to/discs   # RMCE01/sys/main.dol, ...
python3 tools/region/port_map.py --region J --disc-root /path/to/discs
python3 tools/region/port_map.py --region K --disc-root /path/to/discs

# Re-derive the NTSC-J and NTSC-K data tables from the NTSC-U evidence table.
python3 tools/region/port_data_addresses.py --region J --disc-root /path/to/discs
python3 tools/region/port_data_addresses.py --region K --disc-root /path/to/discs

# Resolve every identity the runtime names and write the four region headers.
python3 tools/region/gen_region_headers.py
```

All three are deterministic: running them again over the same inputs reproduces the committed
files byte for byte.

To name a new global in the runtime: write it as `MKW_GADDR(<PAL address>)`, add one row to the
NTSC-U table with the NTSC-U address and the instruction(s) that reference it (`disasm.py` prints
them with the address each `r13`/`r2` access forms), re-run the porter for J and K, then re-run
`gen_region_headers.py`. A new function entry point needs no table row: it ports through the chunk
table and is validated against the region's `MAP.txt`.

Region support is also not the same thing as region *content*: `paths.dvd_root` in `Config.toml`
must point at the extracted disc for the region you are running. A mismatch panics in G3D while
loading textures, which looks like a code bug and is not one.
